# HarborReply v0.1 architecture / ADR

`CODEX_TASK.md` is the original specification, with subsequent user changes recorded in the ADRs. The current release is v0.1.20/build21. Test-only mocks/fixtures remain, while the product and distribution contain no fictional mail or fabricated style examples (ADR-027). Native metadata decoding and timing are separate value-based boundaries (ADR-028); capture selection guidance is distinct from diagnostic codes (ADR-029). External real-data verification and the scoped style budget stopping rule are described in ADR-030. The current deliverable is a local preview application with a Mail diagnostic spike. **It is not yet an accepted automatic Mail insertion workflow.**

## Boundaries and data flow

```text
SwiftUI / AppKit menu + Carbon shortcut / on-device Speech
  → ReplyCoordinator (request UUID, revision, cancellation, expiry)
  → LocalWorker (private stdin/stdout pipes, no shell interpolation)
      → Python email MIME parser → SQLite WAL + FTS5
      → ContextBuilder / Case events / Evidence provenance
  → ResponsesProvider (explicit endpoint, Keychain, no redirects/tools)
  → schema + DraftValidator → local preview
  → AppleMailBridge facade → dedicated serial Apple-event queue
      (explicit capture / opt-in capture; diagnostic only for body insertion)
```

Core state and provider tests do not need Mail, microphones, network, credentials or actual business data. Mail objects stay in a retained static AppleScript instance on its dedicated serial queue. Only parsed Sendable values cross back to the main actor; variable data travels in Apple event descriptors within the queue. No `send`, deletion, move, read-status or account-setting operation is exposed. The user's Copy action writes the validated reply to the clipboard; Mail insertion does not use clipboard or Accessibility injection.

## ADR-001 — MIME and SQLite in a local Python worker

Decision: keep SwiftUI/AppKit and Swift orchestration; use Python's standard `email` and `sqlite3` modules in a bounded local subprocess for archive work. A bespoke Swift MIME implementation would add substantial parsing risk; no third-party parser or SQLite wrapper was added. The worker has no networking or application-control code.

Development builds require Python 3.11 or newer with FTS5 and record the local interpreter path/version. AirDrop distribution supersedes that path with bundled Python 3.14.8 / SQLite 3.53.1, from the pinned astral-sh/python-build-standalone 20261003 release. The package contains only the Apple Silicon runtime and app as requested. Runtime archives are SHA-256 verified; every Mach-O dependency is audited for relocation, each Mach-O is signed, and license notices are retained. A distribution missing its runtime fails closed. No Nix/system configuration was changed. No Swift/pip libraries were fetched. See runtime.lock.json and ADR-006.

Swift language mode 5 with Swift 6.4 was selected for system-framework callback compatibility. UI state is main-actor-owned; archive IO runs off the UI actor; SQLite transactions serialize writers. Search and imports use separate short-lived connections. In v0.1.4, synchronous AppleScript execution moved from the main actor to one dedicated FIFO queue behind async bridge methods. The static script retains its 15-second Apple-event timeout; a blocked event no longer blocks UI input, but cannot necessarily be interrupted after execution begins. See ADR-012 for cancellation and uncertainty handling.

## ADR-002 — Mail range insertion stays a diagnostic

Observed on macOS 27.0.1: Mail.sdef defines `reply`, an `outgoing message` result, sender/To/Cc/Bcc/signature/id, and rich-text paragraphs. The static script compiles. It calls `reply ... opening window yes reply to all ...`, tracks the returned object, snapshots text and envelope fields, rechecks selection and draft, and attempts `make new paragraph at beginning of content`.

**Dictionary presence and script compilation are not runtime evidence.** No selected real/test message was read during development, and no draft was created by the development agent. First use is the app's explicitly initiated diagnostic on a `[HarborReply TEST]` message from `.invalid`.

The dictionary cannot by itself prove that formatting-only edits, inline attachments, S/MIME state and quote boundaries are unchanged. A string snapshot is insufficient proof. `productionMailInsertionVerified` is therefore false. The ordinary insertion and automatic-insertion paths are present but closed. There is no user checkbox that silently bypasses this gate. Verification requires the acceptance matrix, examination of actual failures, and (if necessary) a stronger range-tracking adapter; do not merely flip the flag.

Insertion attempts are one-shot even when completion is uncertain. No automatic draft cleanup or retry follows a possible partial write. Correct replies are never substituted with `mailto:` or a newly reconstructed plaintext message. The app-created draft is left for the user. The test paragraph contains quotation marks, newlines and AppleScript-looking strings as data.

## ADR-003 — conservative case association and context

SHA-256 of parsed message bytes identifies exact copies; Message-ID is only a header relationship key. Locations remain separate. Conflicting Message-IDs remain separate records. Direction comes from user-labeled sources; ambiguous sent/draft duplicates become unknown and cannot become sent facts or style examples.

Header relationships suggest candidates; subjects and ship names do not establish a case. Confirmed manual membership selects history. One thread can have multiple cases and messages can be added/removed. When thread candidates exist without a selected case, generation waits for resolution. This intentionally favors explicit association over a fully automatic case classifier. FTS supplies Japanese single-character/bigram tokens and Latin identifier tokens; search results are added by the user. Semantic search is not implemented.

Events are manually confirmed quoted records. No extra model extraction call is used. Requested/reported/received/checked/approved/held/corrected/cancelled stay separate. Correction references must match case, subject (including lot) and action. Earlier records are retained. Source body hashes and exact quotes are checked before use. Removing membership excludes its events from generation context while retaining the records in the local timeline. Draft and unknown-direction sources cannot become events. No generated response is inserted into archive history.

Context includes current body, all selected case members (up to 100), events, selected sent style examples (up to 3) and registered policy excerpts. Required evidence over 24,000 characters fails closed; current messages over 12,000 characters need narrowing. Optional style examples may be omitted with a warning. These are character limits, not exact model-token accounting. Policy applicability is explicit and scoped to the selected case. Old style facts and internal quotations are excluded by instructions plus limited checks; semantic correctness still requires human evaluation.

## ADR-004 — archive bounds, provenance and deletion

Only user-selected .eml/.mbox files and directories are traversed. Mail export `.mbox/mbox` packages work. Symlinks are rejected, including symlinked parents; explicitly select a physical path if necessary. At most 10,000 directories/files are enumerated. Internal `~/Library/Mail` integration does not exist.

mboxo/mboxrd are streamed using envelope lines; exactly one mboxrd escape is removed. A single file is never split into a whole-corpus string. Limits: 16 MiB per raw mail, 1 MiB line, 250,000 decoded body characters, 16 nested MIME levels, 256 parts. Unsupported `Content-Length` mboxcl/cl2 records fail explicitly. Malformed/encrypted/unknown-charset messages are failures, not imported successes. HTML is reduced to inert text without network access; nested messages and binary/inline attachments are unparsed metadata. Signed MIME signature parts remain unparsed; verification of digital signatures is not implemented.

A batch commits messages, locations and checkpoint together. Re-running uses the checkpoint; parser/fingerprint changes require deliberate deletion and re-import. Device/inode/size/mtime/ctime detect source changes, and exact raw-range hashes are checked when opening evidence or generating. This is a snapshot and not a backup or live synchronization.

Source deletion removes locations and now-unreferenced messages, FTS rows, events, memberships and style links with cascading foreign keys. Other exact-copy locations survive. SQLite secure_delete, WAL checkpoint/truncate and VACUUM run; OS backups, SSD blocks and snapshots are outside secure-erasure claims. Settings/policies are independently retained until their own explicit deletion.

## ADR-005 — API and voice

The original adapter is OpenAI Responses-compatible HTTPS with Structured Outputs, explicit model, `store:false`, no tools, ephemeral URLSession and no redirects. API keys are Keychain entries scoped to the exact endpoint. No API key is passed to a process or stored in JSON. One retry is allowed for HTTP 429; other status/network/timeout failures surface sanitized codes. Refusals, incomplete outputs, malformed JSON and schema/evidence failures never insert. API-key generation is non-streaming. ChatGPT-plan generation added in ADR-007 uses bounded SSE; first-token timing is still unmeasured. Normal generation uses one inference call, excluding that bounded API-key 429 retry.

The schema lives in `worker/contract.py` and is used for both the provider request and local shape validation. Validation checks exact evidence quotes, body spans, some numeric/date/ship/policy tokens, internal/header leakage and common Japanese prohibitions. It is **not a semantic proof**. Generation requires an explicitly enabled, configured real provider. No fixed reply generator or alternate local generation route is shipped.

Speech uses the installed SDK's SFSpeechRecognizer, with Japanese locale, `supportsOnDeviceRecognition` and `requiresOnDeviceRecognition=true`. SpeechAnalyzer was not needed for this slice. If local recognition is unavailable, no cloud fallback occurs. Microphone/Speech permissions are requested only after pressing record. No audio file is created. Stop waits for a final result; the user can correct it and presses Generate. Automatic generation immediately after speech stops is deliberately deferred until recognition uncertainty behavior is tested. Partial results never generate a reply.

## ADR-006 — AirDrop package and opt-in diagnostics

The user requested installation on a friend's Apple Silicon Mac by AirDrop. `scripts/package-app.py` creates an arm64 app plus install guide and a fictional test mail, in a ZIP. It never copies Application Support, developer credentials, history, logs or Git data. `runtime.json` containing the local interpreter path is removed. This is an ad-hoc signed development preview, not notarized; the owner's normal macOS approval flow and permissions are still required. Intel is excluded by explicit request.

Diagnostics are OFF by default, enabled only by a visible local toggle. The Swift log schema admits typed event/phase/failure enums, bounded numbers, times and a random session UUID only. It cannot accept a free-text message, path, URL, email address or source identifier. Files rotate at approximately 1 MiB each, at most two; directory 0700, files 0600. No remote log service is installed. AirDrop can return those logs manually. `scripts/watch-logs.sh` can follow them over an already authorized SSH connection, with host-key checking; it does not enable sharing or open firewall ports. No owner consent to remote access or remote destination has yet been provided, so no live connection was made.

## ADR-007 — Sign in with ChatGPT (explicit user scope addition)

The user requested using their ChatGPT plan. Implemented the official direct OAuth flow for locally hosted apps, not a Codex subprocess. The app opens the system browser only on **Sign in with ChatGPT**. It binds a temporary listener to 127.0.0.1 on an ephemeral port, keeps `/auth/callback` constant, sends fresh cryptographic state/nonce/S256 PKCE, and uses dynamic client registration with a persistent per-install opaque UUID host ID. Callback consumption is one-shot, timeout/cancel closes the listener, and callback response pages never echo credential data. Issued client IDs and verified subjects bind separate account registrations; returning login reuses them, new login never changes the active account until validation succeeds. An issued client ID is kept for retry if exchange fails during that attempt.

ID tokens are RS256-verified with Apple's Security framework against the pinned OpenAI JWKS; issuer, audience/authorized party, expiration, issued-at, not-before, nonce and returning subject are checked. OAuth access/refresh/ID tokens and account mappings are atomically stored as a Keychain item, never in settings JSON, process arguments, diagnostics or the package. Refreshes are coalesced per session, rotate credentials together and reject late results following sign-out or a new login. Sign-out clears local tokens, attempts revocation through the validated discovery endpoint with one retry, and reports when remote revocation is unconfirmed. Registration mappings and host ID remain for reauthorization.

The model picker uses the account's `/v1/models` response and `visibility=list`, preserving order. Inference uses only `https://api.openai.com/v1/responses`, `store:false`, `stream:true`, array input, strict JSON schema and no tools. Unsupported plan-route fields such as `max_output_tokens` are omitted. A completed response is required before ordinary local draft validation. The response stream is bounded at 12 MB and 120 seconds. Plan permission is checked before requests; failures never switch billing paths or Mock. Onboarding consent remains separate from the app's explicit mail-disclosure toggle. Current browser consent, plan eligibility, model compatibility, token refresh/revocation and output quality remain unverified against a real account.

References: [registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), [UI guidance](https://developers.openai.com/siwc/ui-ux-guidelines). The live unauthenticated discovery/JWKS endpoints were inspected and reported issuer auth.openai.com, RS256 and the documented token/revocation endpoints. No real credentials or mail were used.

## ADR-009 — bounded retrieval and precomputed style (2026-10-09)

The normal input is selected mail + related mail + style + intent → one reply. Behind it, the user-selected archive produces related-mail candidates via header/index lookups, confirmed case membership and bounded FTS. It produces style only from deliberately selected, author-confirmed sent examples. No whole-corpus LLM, embedding or automatic shared-mailbox authorship inference is added.

Previously every context called `status()`, doing a whole-message aggregation and all-source stat; confirmed-case retrieval sorted/fetched all rows before checking its bound; FTS BM25 ranked every matching row before LIMIT. Coverage now uses maintained totals and indexed date endpoints. A covering case/date index with LIMIT101 detects oversized cases without fetching them all. FTS reverse rowid order stops after bounded candidates and carries a query budget. This trades global relevance ranking for most-recently-indexed matching candidates; it is neither date ranking nor a relevance-quality improvement claim. The user must still confirm case association. Scope limits do not silently discard important corrections or mark missing histories complete.

Numeric style features are persisted when examples change. They contain only format/language statistics, never old ship names, dates, decisions or quotations. v0.1.4 separates those numbers from a prose description and synthetic templates: only an explicit extraction command creates the latter (ADR-011). The manual style remains editable and takes precedence. Style source ranges are verified during generation; changed/missing sources fail closed. Old DBs migrate once; migration and explicit deletion/VACUUM may be linear. Detailed costs, regression gates and limits are in [PERFORMANCE.md](PERFORMANCE.md).

## ADR-011 — explicit background style extraction (2026-10-10)

The reply view shows the stored style description and illustrative examples alongside the related-mail summary. Only the user's Extract/Re-extract action runs `style_extract`, using at most three explicitly author-confirmed sent messages. A local deterministic formatter turns numeric characteristics into a short description and synthetic templates with placeholders. It does not copy source text into those templates or call a model. A separate `source_phrases` field carries up to three exact neutral greeting/closing lines found in the selected sources; strict full-line allowlisting prevents names, numbers, approvals and partial/quoted lines from entering it. The UI labels source phrases separately from synthetic templates. No matching phrase means no purported source example. Reply preparation and overview reads never trigger prose extraction. Manual style instructions take precedence.

An operation UUID, archive epoch and mode guard reject late extraction results after cancellation, example changes or real/demo switching. Example changes mark a previous description stale; changed source ranges also invalidate it. Previously generated replies become unusable until regenerated after style changes. Failed re-extraction clears the old visible description, surfaces the failure and invalidates the current reply rather than hiding the failure behind an earlier ready summary. The optional selected source texts remain separate `style_examples` in the explicitly enabled provider input, subject to the existing context budget. This is not whole-archive authorship analysis or a claim that selected example text never leaves the device.

## ADR-012 — asynchronous Mail bridge and opt-in panel capture (2026-10-10)

The main-actor facade exposes async capture/create/snapshot/insert methods. Its queue-owned engine creates and uses all NSAppleScript and NSAppleEventDescriptor objects on one serial queue; only immutable parsed values cross the boundary. A lock-protected operation gate atomically authorizes each event. Cancellation before that permit suppresses the event, including queued writes. Cancellation after a create/insert permit conservatively reports that the write may have completed. Clearing tracking advances a facade epoch, cancels existing gates immediately and queues state cleanup in FIFO order. Late values cannot become the current reply; an uncertain write still produces a content-free notice even for a cancelled request. No retry or draft deletion follows it.

Automatic capture is a persisted opt-in, OFF by default. On application launch or an explicit panel opening, it requires already-running Mail, successful `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)` on the worker queue, an unchanged request and no intent, reply, tracked draft, busy/importing/recording operation, demo or self-test. It never starts Mail, prompts automatically, polls while idle or recaptures merely because the app becomes active after OAuth. Explicit Capture and the initial user action enabling this preference use the ordinary OS permission flow. This extends capture only; production body insertion remains disabled pending the Mail acceptance matrix.

Threading reference: [Apple DTS on serialized secondary-thread NSAppleScript](https://developer.apple.com/forums/thread/759287); the installed Xcode 27 SDK's AppleEvents.h documents the permission preflight as thread-safe and unsuitable for the main thread. Real Mail latency, permission behavior and range safety remain unverified.

## ADR-015 — bounded native Mail history and confirmed Sent examples (2026-10-10, v0.1.7)

The user's revised workflow permits fetching the relevant Mail history and sent examples in the app, without first exporting files. Selection capture starts bounded read-only metadata retrieval in the selected account: selected mailbox, Inbox and Sent, at most three mailboxes, first/last windows totalling at most 256 headers per mailbox (768 overall). Mail's mailbox ordering is not guaranteed. This window is incomplete and is not a complete date range, whole-Mail search, service synchronization or 300GB acceptance. Only up to 20 ranked candidates are hydrated; attachments are not fetched. Candidates remain suggestions with reasons and scope, not confirmed case membership, events, approvals or assertions that missing history does not exist.

Style extraction remains a user action in the style island. It uses the selected account, or the only enabled account when there is no target; multiple accounts without a target fail closed and require selecting a Mail message. On first use the owner explicitly confirms that account as personally authored. Eligibility requires actual Sent-mailbox provenance, a sender among that account's addresses, and exclusion of configured shared addresses. From matching alone is insufficient. At most three newest eligible examples within the bounded fetched window are hydrated, then quoted/forwarded portions are excluded from local style extraction. Re-extraction fetches a fresh bounded window rather than silently reusing a style cache. Ordinary target capture does not extract or update style automatically. Unknown/shared authorship is not learned automatically. This deliberately adds user-triggered native Sent sampling to the specification's export/selected-example scope; unattended continuous style learning stays deferred.

Hydrated messages become immutable, content-addressed .eml snapshots under the application's private `mail-snapshots/` directory beside its SQLite database. Snapshot provenance is `apple_mail_readonly_snapshot`; original Mail identifiers/account/mailbox scope and unacquired attachments remain distinct from fully exported MIME. Direct `~/Library/Mail` access and account-setting mutation are absent. Directory/file modes are 0700/0600; neither SQLite nor snapshots are automatically encrypted. A snapshot does not prove the live Mail source stayed unchanged after capture. Retrieval, indexing and local style extraction do not call an external model. Existing explicit cloud-disclosure consent is still required before generation can transmit its bounded input. Mail read operations remain on the bridge's serial queue, with cancellation/request/revision/operation guards; production insertion remains disabled and there is no sending API. Actual Mail account/Sent mapping, ordering, latency, permissions and authorship quality require owner testing and are not established by fictional bridge tests.

Only the app-owned database parent is canonicalized when constructing the snapshot storage path. Foundation can spell `/private/var` as `/var`; resolving that parent prevents the app's own immutable snapshots from being rejected as redirected imported sources. The `mail-snapshots` leaf remains unresolved and rejects symlink redirection. User-selected source paths still reject symlink components; this is not permission to follow aliases in imported mail.

Metadata ranking and snapshot persistence use serialized-row batches capped at 1,500,000 bytes, leaving room under the worker's 2MiB request envelope. Ranking receives current-message metadata without its body. Native body hydration remains bounded to 20 messages and 2MiB per message; local snapshots accept bodies up to 12,000 characters and headers up to 32,768. Oversized candidates/examples are excluded with a visible count rather than truncated into apparent complete evidence. If no eligible Sent example fits, extraction fails explicitly. These application caps do not establish Mail's internal retrieval cost or source completeness.

## ADR-016 — local ranking over bounded candidate pools (2026-10-10, v0.1.7)

The AWS retrieval report is a keyword/relevance example, not a request to connect to Amazon Web Services. A pure local scorer ranks a bounded pool using subject, sender/address domain and query terms, including the explicit lexical equivalence AWS ↔ Amazon Web Services. AWS provider identity requires an explicit AWS/Amazon Web Services subject or sender display name, or an exact/subdomain match under `amazonaws.com` or `aws.amazon.com`; general Amazon retail and sender/domain matching alone do not establish AWS relevance. Native metadata is ranked before body hydration. Local archive search uses at most three FTS query lanes of LIMIT60: provider/topic terms, provider-only terms and subject/domain terms as available. After deduplication at most 180 metadata rows are scored/sorted. A 200,000 SQLite VM-step/0.75-second budget fails explicitly rather than reporting a partial search as complete. It never requests a global BM25 sort of every matching archive row or sends the corpus to a model/search service. Header/case provenance and confirmed facts remain separate from relevance scores.

This supersedes ADR-009's single recent-row FTS order with ranking inside a bounded candidate pool. It improves the particular candidate selection mechanism without promising global relevance or complete recall outside the fetched window. Performance checks must measure pool size, SQL work and synthetic sizes; real Mail window traversal may still depend on Mail's implementation. Neither small fixtures nor the existing 100k synthetic archive establish 300GB behavior. Exact measured results belong in VERIFICATION.md/PERFORMANCE.md once integration checks finish.

Newly indexed messages add sender terms to FTS. Existing archives are not automatically rescanned/reindexed on launch, so sender-only recall on old rows is limited; provider terms in already-indexed subjects/bodies remain searchable. ## ADR-031: One window owns reply and settings

The owner asked to remove a separate empty window. The application declared an unused `SwiftUI.Settings { EmptyView() }` scene even though its real settings already live inside the retained main NSWindow. Remove that scene and use an AppKit entry point retaining AppDelegate for the application's lifetime; content remains native SwiftUI. Standard responder-chain editing/close shortcuts have explicit menus, and Command-comma opens actual settings in the same retained window. Reopening, capture and settings share that window.

A content-free System Events check observed one main HarborReply window and no untitled/settings windows in the owner's running v0.1.17 process. It did not identify the reported separate window, so its current origin is unconfirmed. No other application's windows, real Mail contents, credentials, screenshots or owner state were inspected/changed. This change prevents the unused settings scene; interactive startup/Command-comma/editing acceptance of the new build remains separate from build success.

## Sparkle distribution and mandatory-update boundary — 2026-10-12

User-authorized extension of the original v0.1 distribution scope: `nix run .#deploy` now publishes signed/notarized releases; `.#package` retains the local, unnotarized handoff. Sparkle 2.9.6 is pinned in Package.swift/Package.resolved, embedded with inside-out nested-code signing and its full license. Native app construction uses host Xcode outside the Nix store. Signing keys and Apple/GitHub credentials stay in Keychain/credential managers; release.json contains public settings only.

Info.plist is the sole version/build source. A clean source commit plus public release.json produces a notarized application ZIP, signed appcast, separately Ed25519-signed policy envelope and provenance/checksum manifest. Artifacts upload to a draft in a separate public GitHub distribution repository. The archive must pass anonymous download verification before one fast-forward Git commit publishes appcast/policy on the updates branch. Source code is never pushed by deploy. No asset clobbering; exact prepared artifacts are reused on --resume. Concurrent publication cannot force-push a newer feed away. Source changes during preparation stop publication. A local failed preparation is never automatically deleted or silently rebuilt over a completed release.

The application trusts a fixed HTTPS feed and an embedded public key, not GitHub's Latest label. Sparkle verifies signed feeds and archives; CryptoKit verifies raw policy bytes before decoding. Policy schema/build/sequence/date constraints and cached sequence prevent accepting malformed or older policies. Cached signed envelopes retain their original expiry on network errors. Missing/expired policy disables new generation/prepare/insert, retaining current text and copy availability. Release policy defaults to the current build becoming mandatory after 72 hours and policy expiration after 90 days; continued maintenance must publish before expiry. The mechanism does not prevent local-admin modification, clock manipulation, or update-capable clients never connecting before their cached expiry.

AppUpdater owns network/timer/Sparkle effects; HarborCore.UpdatePolicy is pure verification/decision logic. Development builds omit update endpoints and perform no updater networking. Scheduled relaunch and NSApplication termination both refuse while work/recording/text remain; manual checking provides explicit text-discard confirmation after the user copies it. This intentionally keeps text in the running process rather than introducing plaintext draft persistence. Production Mail insertion verification and request/revision checks are unchanged. Binary relocation checks exit on an unsupported flag before coordinator/Mail/preferences initialize; synthetic data and signing keys exist only in tests, not the shipped product.

GitHub raw hosting avoids a separate Pages setup. CDN caches can delay each request, so a Git-atomic publication is not claimed to give clients an atomic two-request snapshot. Policy expiry and archive availability are independently enforced. Mandatory policy changes require a new increasing build; recovery uses a higher build carrying reverted source, not a downgrade or asset replacement.

## Direct Mail store reader — 2026-10-12

Explicit owner permission supersedes the default prohibition on reading Library/Mail for this feature. Normal archive indexing now uses a separate HarborMailReader process, forced through sandbox-exec with filesystem writes and networking denied. MailStoreReadOnly exports opaque read capabilities without paths, descriptors or mutation methods; all opens use O_RDONLY and component-wise O_NOFOLLOW. The preservation argument applies to clients using this closed API, not arbitrary unsafe Swift, other processes, or a formal proof of Darwin. Compile-negative API tests and sandbox mutation-denial tests cover that boundary. Reply insertion remains on the existing fail-closed Mail bridge.

No archive export or attachment payload is persisted. EMLX MIME feeds the existing parser and app-owned SQLite FTS5. Discovery is O(files); unchanged fingerprints skip content; changed content alone is parsed. Successful full traversal retires missing entries; interrupted traversal never does. Read-time fingerprint and directory-change checks prevent claiming a coherent completed sweep after observed changes. This is not FSEvents/O(delta) discovery. Direct records have unknown direction and cannot establish sent-style/factual evidence without a trusted direction mapping. Per-message MIME remains capped at16MiB; incomplete/unsupported files are explicitly unindexed and retried.

Relocation exposed an ad-hoc-only library-validation failure: Hardened Runtime cannot treat separately ad-hoc-signed app/framework code as one Developer ID team. Local ad-hoc builds now omit Hardened Runtime. Actual identity-signed builds and deploy retain runtime + secure timestamp; no disable-library-validation entitlement or production security bypass was added. External standalone Mail/style verification harnesses exclude AppUpdater along with App.swift, avoiding updater networking and an unnecessary Sparkle dependency in those owner-started tools.

Related-mail retrieval now uses service-neutral subject-term overlap and exact sender equality, retaining reply-header priority. Removed brand aliases, provider-domain lists, provider fallbacks, and hand-authored topic categories. Generic bounded FTS conjunction/pair/disjunction queries replace service-specific queries; no new LLM or embedding stage was added.

The reply UI now sends an explicit related_selection (excluded IDs). Retrieved available candidates default to selected; toggles invalidate the reply revision, and a new target resets exclusions. This mode does not require case membership. Unknown/draft direction is retained and explicitly disallowed as proof of sending/approval in model instructions; legacy case-mode validation remains unchanged. Long selected bodies use bounded leading excerpts with a visible notice. Index management is separate in Settings; the reply card is selection/preview only.
